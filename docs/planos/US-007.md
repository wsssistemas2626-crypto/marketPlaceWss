# Plano — US-007 [ENABLER] Idempotência e rate limit

**Story:** US-007 · **Referências:** CLAUDE.md §4.10 (Idempotency-Key obrigatório em criação e
movimentação de dinheiro) e §4.12 (rate limit por tenant), `06-multi-tenancy.md` §4.

## Peças (`packages/platform/src/http`)

| Arquivo | Conteúdo |
|---|---|
| `idempotency.ts` | `runIdempotent`: executa uma vez por chave, repete a resposta guardada, 409 se a mesma chave vier com outro corpo, apaga o registro em caso de falha; TTL de 24 h |
| `redis-idempotency.store.ts` | `SET NX PX` (atômico) para duas requisições simultâneas não iniciarem o mesmo trabalho |
| `idempotency.interceptor.ts` | decorator `@Idempotent()` e interceptor que exige o header nas rotas marcadas |
| `rate-limit.guard.ts` | `RateLimitGuard` contando **IP, usuário, API key e tenant**, com `@RateLimit()` por rota e header `Retry-After` |

## Decisões

1. **A chave de idempotência é escopada por tenant** (`t:{tenantId}:idempotency:{chave}`): a mesma
   string vinda de tenants diferentes é outra operação.
2. **Corpo + rota entram na impressão digital**: reusar a chave com outro corpo é erro do cliente, não
   um replay — devolver a resposta antiga aí esconderia um bug.
3. **Falha apaga o registro**: erro transitório (gateway fora do ar) precisa poder ser tentado de novo
   com a mesma chave.
4. **Quatro dimensões de rate limit** porque resolvem coisas diferentes: IP contém abuso anônimo,
   usuário/API key contêm um cliente, e a cota por tenant é o que o plano vende (US-073).

## Verificação manual feita

```
POST /v1/store/widgets sem Idempotency-Key              -> 400 idempotency_key_required
POST com Idempotency-Key: k-1                            -> 201
POST repetindo k-1 com o mesmo corpo                     -> 201 com o MESMO id (replay, sem criar outro)
POST com k-1 e corpo diferente                           -> 409 idempotency_key_reused
```
Todas as respostas de erro trazem `correlation_id`, e a resposta traz o header `x-correlation-id`.
