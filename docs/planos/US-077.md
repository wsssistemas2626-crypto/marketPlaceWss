# Plano — US-077 Tema e identidade visual do tenant

**Story:** US-077 · **Referências:** RF-TEN-04, `arquitetura/06-multi-tenancy.md` §10 (white-label),
CLAUDE.md §9 (sem código customizado por tenant).

## Desenho

| Peça | Onde |
|---|---|
| Tokens de design validados por Zod | `tenancy/src/domain/theme.ts` |
| Rascunho × publicado | `tenancy.themes` (uma linha por tenant, RLS) |
| Casos de uso | `ThemeService`: `getDraft`, `saveDraft`, `publish`, `discardDraft`, `getPublished` |
| Rotas do admin | `GET/PUT /v1/admin/theme`, `POST /v1/admin/theme/publish`, `POST /v1/admin/theme/discard` |
| Rota da loja | `GET /v1/store/theme` (tenant vem do host, sem autenticação) |
| Aplicação no storefront | `apps/storefront`: variáveis CSS no `<body>` + título/favicon do tenant |

## Decisões

1. **Lista fechada de tokens, não CSS livre.** Aceitar CSS arbitrário de um tenant seria entregar execução
   de estilo (e, com `url()`, exfiltração) numa página servida pela plataforma. Cor precisa ser hexadecimal,
   fonte vem de uma lista permitida, logo e favicon só por `https`. Tem teste para cada recusa.
2. **Rascunho e publicado lado a lado.** Sem isso, mexer numa cor apareceria para os compradores no mesmo
   instante. O preview do admin lê o rascunho; a loja lê o publicado.
3. **Tenant sem tema recebe o padrão** — a loja nunca fica sem estilo, nem durante o provisionamento.
4. **O storefront não fala com o banco**: pede o tema à API (CLAUDE.md §9), e falha de rede cai no tema
   padrão em vez de derrubar a página.

## Bug encontrado e corrigido no caminho

A primeira versão do storefront repassava o `Host` do visitante para a API com
`fetch(url, { headers: { host } })`. **Não funciona**: `Host` é *forbidden header name* no Fetch e o runtime
o descarta em silêncio — a chamada chegava como `localhost:3100` e a API respondia 404 "loja não
encontrada". A correção usa o mesmo mecanismo do edge (ADR-014 §6): `X-Forwarded-Host` acompanhado de
`X-Edge-Secret`, que a API só aceita quando o segredo confere. Ficou em `apps/storefront/lib/api.ts`, com o
motivo escrito no comentário para ninguém "simplificar" de volta.

## Testes

12 unitários: padrões, recusa de cor não-hexadecimal, fonte fora da lista, URL não-https, raio/peso fora de
faixa, geração das variáveis CSS, rascunho não afeta a loja, publicar leva o rascunho ao ar, descartar
restaura, isolamento entre tenants e rascunho inválido não chega ao banco.

## Verificação manual

```
GET  /v1/store/theme (Host: loja-a.localhost)   → tema padrão
PUT  /v1/admin/theme {"colors":{"primary":"#e91e63"},"brand":{"storeName":"Loja A Fashion"}}
GET  /v1/store/theme                            → ainda o antigo (é um rascunho)
POST /v1/admin/theme/publish
GET  /v1/store/theme                            → #e91e63
storefront (Host: loja-a.localhost)             → --mkt-color-primary:#e91e63, <title>Loja A Fashion</title>
storefront (Host: loja-b.localhost)             → --mkt-color-primary:#1f6feb, <title>Storefront</title>
```
