## Verificações feitas localmente

- `docker build` da api e do storefront: as duas imagens sobem.
- Container do storefront respondendo `GET /api/health` → 200, escutando em `[::]` (armadilha #2).
- **As migrações chegam na imagem**: `packages/*/drizzle/*.sql` e `packages/modules/*/drizzle/*.sql` estão
  presentes no estágio final, que é o que faz o `preDeployCommand` funcionar. Conferido com
  `docker run --entrypoint sh` listando os arquivos.
- `dist/migrate.js`, `dist/seed-dev.js` e `dist/main.js` presentes na imagem da api.

## O que **não** foi executado (e por quê)

Nada foi criado na Railway. A seção B do checklist está inteira pendente (conta Pro, projeto, ambientes,
CLI, serviços de dados, bootstrap de roles, shared variables) e não existe credencial de Railway neste
ambiente. Além disso, o CLAUDE.md §4.18 proíbe o agente de criar/apagar recursos de infraestrutura sem
confirmação explícita.

Os cenários Gherkin da story que dependem do deploy real — merge no main publicando staging, ambiente de PR
com seed, migração falhando abortar o deploy, e a confirmação de `rolsuper = false`/`rolbypassrls = false`
em produção — ficam para a primeira execução após a configuração da conta. O runbook traz exatamente os
comandos de verificação.

## Decisões

1. **`watchPatterns` por serviço** para um push em `apps/admin` não reconstruir a api inteira.
2. **Seed só no ambiente `pr`**: em `staging` o banco é persistente e um seed a cada deploy sobrescreveria
   dados fictícios que alguém está usando.
3. **`overlapSeconds: 20` + `drainingSeconds: 30`** na api (60 s no worker): a versão nova recebe tráfego
   antes de a antiga morrer, e a antiga tem tempo de terminar o que começou (armadilha #5).
