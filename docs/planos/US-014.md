# Plano — US-014 Endereços do comprador

**Story:** US-014 (P) · **Referências:** RF-IAM-09, RNF-SEG-03 (IDOR), `03-integracoes.md` (`PostalCodePort`, dono
`identity`), CLAUDE.md §4.4 (adapter fora do módulo).

Critério da story: CEP via `PostalCodePort` (adapter ViaCEP + fake).

```gherkin
Cenário: cadastrar endereço com autocompletar
  Dado que estou logado na loja
  Quando informo o CEP 01001-000
  Então rua, bairro, cidade e UF são preenchidos, e eu completo número e complemento

Cenário: endereço padrão
  Então o primeiro endereço é o padrão, marcar outro desmarca o anterior e remover o padrão promove o mais recente

Cenário: IDOR
  Dado o id de um endereço de outro comprador
  Quando tento editar ou remover
  Então recebo 404, e o endereço não muda

Cenário: serviço de CEP fora
  Então vejo um aviso e preencho à mão (503, não 500)
```

## Desenho

| Camada | Peça |
|---|---|
| Contrato | `PostalCodePort`/`PostalCodeAddress` em `@mkt/contracts` (como os demais ports enquanto o dono não os hospeda) |
| Adapters | `packages/adapters/postal-code-viacep` (novo, sem dependência: `fetch` com timeout de 3 s); `FakePostalCode` em `adapters-fakes` |
| Domínio | `address.ts` — validação e normalização (CEP 8 dígitos, UF da lista, tamanhos, "S/N") |
| Aplicação | `CustomerAddresses`: listar, adicionar (limite de 20), editar, remover, padrão, consultar CEP |
| Infra | migração `0005_customer_addresses.sql` (RLS, índice único parcial do padrão), repositório que filtra por comprador |
| HTTP | `GET/POST /v1/store/customers/me/addresses`, `PUT/DELETE …/:id`, `GET /v1/store/postal-codes?zipCode=` — todos `@CustomerAuth` |
| Storefront | `/conta/enderecos` com autocompletar no `blur` do CEP |

## Decisões

1. **O dono vem da sessão, não do caminho** (`/customers/me/addresses`); o repositório filtra por comprador **e** a
   RLS pelo tenant. Id de outro comprador = 404 (não 403: não confirma que existe). Id malformado também é 404.
2. **CEP não é integração por tenant**: todo marketplace usa o mesmo serviço, escolhido pelo host
   (`POSTAL_CODE_PROVIDER`, padrão `viacep`; `fake` nos testes). Por isso não passa pelo hub.
3. **CEP só para comprador logado, com limite por cliente** — aberta, a rota viraria um proxy do ViaCEP em nome da
   plataforma. Query string (`?zipCode=`) em vez de parâmetro de caminho: a suíte de isolamento só sabe preencher `:id`.
4. **Serviço fora = 503 com mensagem de preenchimento manual**; CEP inexistente = `found: false`. CEP geral de cidade
   (sem rua/bairro) preenche só cidade e UF.
5. **Pacote de adapter novo sem `pnpm install`**: com o `pnpm dev` rodando, o `node_modules` do pacote foi ligado por
   junction (mesmas dependências do `domains-cloudflare`) e o lockfile ganhou as entradas equivalentes. Um
   `pnpm install` normal recria tudo igual.
