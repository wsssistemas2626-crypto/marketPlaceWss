# Spike US-085 — Domínio próprio de tenant via Cloudflare for SaaS → Railway

**Status:** ⚠️ **Parcial — conclusão pendente de validação real.** Timebox de 2 dias previsto no backlog;
o que dependia de código está pronto e testado, o que dependia de conta não pôde ser executado.
**Data:** 2026-09-22

## Pergunta do spike

> Um domínio próprio de tenant (`loja-teste.com.br`) chega ao storefront certo, com HTTPS válido, sem
> quebrar cookies, redirects, canonical e sitemap — e sem que alguém consiga se passar por outro tenant?

## O que foi construído

| Entregável | Onde | Estado |
|---|---|---|
| Cloudflare Worker do edge | `infra/cloudflare/worker.js` + `wrangler.toml` | pronto, com testes |
| Adapter `domains-cloudflare` (`DomainProvisioningPort`) | `packages/adapters/domains-cloudflare` | pronto, com testes |
| Defesa contra falsificação de host | `resolveRequestHost` em `@mkt/platform` (US-070) | pronto, com testes |

### O caminho desenhado

```
navegador → loja-x.com.br
          → Cloudflare for SaaS (Custom Hostname + certificado DV)
          → Worker do edge  ── define X-Forwarded-Host: loja-x.com.br
          │                 └─ define X-Edge-Secret: <EDGE_SHARED_SECRET>
          → edge-origin.<plataforma> (único host cadastrado na Railway)
          → storefront → resolve o tenant pelo X-Forwarded-Host (só com o segredo válido)
```

O desenho existe porque a Railway limita domínios customizados por serviço (20 no plano Pro) e a própria
documentação dela recomenda gerenciar domínios de cliente fora. Um hostname fica cadastrado lá; o resto é
Cloudflare.

## O que já está **provado automaticamente**

| Cenário | Como |
|---|---|
| **Tentativa de falsificar o host** (2º cenário do Gherkin) | `tenancy.test.ts`: `X-Forwarded-Host` sem `X-Edge-Secret`, ou com segredo errado, é **ignorado** e o tenant sai do `Host` real. Também coberto quando o processo não tem segredo configurado. |
| Worker marca a requisição corretamente | `edge-worker.test.ts`: `X-Forwarded-Host` = host do visitante, `X-Edge-Secret` presente, query preservada, origem reescrita para `edge-origin`. |
| Redirect não vaza o domínio interno | `edge-worker.test.ts`: `Location` absoluto apontando para a origem é reescrito para o domínio do tenant; `Location` relativo passa intacto. |
| Worker sem configuração não encaminha | `edge-worker.test.ts`: responde 500 em vez de mandar requisição sem segredo. |
| Ciclo de vida do hostname na Cloudflare | `cloudflare-domains.test.ts`: registro idempotente, tradução dos estados, remoção idempotente, erro traduzido. |

## O que **não** foi validado (e por quê)

Nada disto pôde ser executado: exige o que a seção C do checklist ainda não tem — domínio registrado, DNS no
Cloudflare, Cloudflare for SaaS habilitado com token, e o serviço rodando na Railway (seção B).

1. **Certificado emitido de verdade** para um hostname de cliente, e o tempo até ficar ativo.
2. **Cookies de sessão do comprador** no domínio do tenant (atributos `Domain`/`SameSite` atravessando o Worker).
3. **Canonical e sitemap** saindo com o domínio do tenant — depende do storefront da Fase 1, que ainda não
   renderiza páginas de produto.
4. **Cache**: o que a Cloudflare guarda por hostname e se isso pode misturar resposta entre tenants.
5. **Latência real** do salto extra (Worker → origem única).

## Recomendação

**Seguir com o desenho**, com duas ressalvas registradas para a US-078:

1. **Cache é o risco aberto.** Um `Cache-Control` público numa rota que varia por tenant, com a origem única,
   é a forma mais provável de vazar conteúdo entre tenants nesta arquitetura. A US-078 precisa começar com
   `Cache-Control: private, no-store` no storefront e liberar cache por rota, conscientemente, com `Vary` no
   host — e a suíte de isolamento deve ganhar um caso que exercite duas requisições de tenants diferentes
   pela mesma aresta.
2. **O segredo do edge é o ponto único de confiança.** Se `EDGE_SHARED_SECRET` vazar, qualquer um se passa por
   qualquer tenant. Ele precisa de rotação documentada no runbook e nunca pode ir para o cliente. A alternativa
   mais forte (mTLS entre Cloudflare e origem, via Authenticated Origin Pulls) fica anotada como evolução na
   US-086.

**Alternativa Vercel:** não descartada, mas não há motivo para trocar — a origem já está na Railway (ADR-014) e
mover só os domínios para a Vercel somaria um terceiro fornecedor sem resolver nenhum dos dois riscos acima.
